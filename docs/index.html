Gallery Maker

Create lightweight photo galleries

Gallery Maker is a simple tool for organizing and generating photo galleries from local files. Instead of bundling a heavy desktop runtime like Electron, it takes a deliberately lightweight approach: Gallery Maker spins up a local Node.js server and opens its user interface right in your default browser. This gives you a local desktop-like experience without shipping an embedded browser.

A Desktop App Without Electron

On startup, Gallery Maker launches a local web server and automatically opens the app in your default browser. The UI runs in a familiar browser tab while the backend handles gallery generation and file system access—no Electron or separate browser runtime required.

A WebSocket heartbeat keeps the open tab connected to the local server. If you close the tab, the server detects the disconnect and automatically shuts down after a brief grace period (allowing quick page reloads without accidentally killing the process). To prevent state conflicts, the app is designed for a single active session: opening it in a second tab displays a notice and prevents concurrent usage.

Local File Access via File Service

For security reasons, web pages cannot directly access your computer's file system. Gallery Maker solves this with a server-side local file service. The browser UI communicates with this service through the local server's API to browse directories, select images, and read or save gallery projects.

This file service acts as the bridge between the browser interface and your local photos. Everything stays completely local on your machine: the app works directly with your selected files to generate a ready-to-use gallery.

Lightweight UI with VanJS

Gallery Maker builds its user interface using VanJS. This ultra-lightweight JavaScript library enables direct, reactive DOM manipulation without the overhead of a large UI framework or heavy runtime. Combined with Bootstrap and vanjs-bootstrap for styling and UI components, the client side stays clean, fast, and minimal.

Smooth Development Workflow

The development setup is built for fast iteration:

  • npm run dev: Starts the server in development mode and watches both server and client files. Client changes are automatically rebundled with esbuild (supporting live reload), while changes to server files trigger an automatic server restart.
  • npm start: Starts the local server for normal usage and opens the app in your browser.

From Local Photos to Ready-to-Use Galleries

At its core, Gallery Maker focuses on a clear workflow: pick your images, organize them into a gallery project, and generate the final photo gallery. You can preview the result directly inside the app or open it in a separate browser tab.

By combining the accessibility of a web UI with local file system access—and skipping Electron in favor of VanJS—Gallery Maker keeps its architecture lean while giving you direct control over your own photos.

Gallery Maker Manual

This program is used to create photo galleries for the web. You can create multiple projects. Each project represents a photo gallery and is saved as a single file (with the ".gmp" extension). Access is provided via the standard "File" menu:

  • New (create a new project)
  • Open (open an existing file)
  • Recent files
  • Save
  • Save As

The "Save" option is largely redundant, as changes are saved automatically. Closing the browser tab also terminates the background service. Since data is always saved, the application will restore its previous state the next time you open it.

The menu allows you to switch between the "Project," "Images," and "Gallery" views.

Project

Here, you can specify the title of the gallery page and the name of the HTML file (the default, if no name is provided, is "index").

You can also select the destination directory where the gallery will be saved. The current project filename is displayed.

Images

This section displays the gallery's images in a list. You can change their order and rotate the images.

Each image can be assigned a caption and an optional, more detailed description.

Use the "Add Images" menu option to include images in the list.

To make sorting easier, a "compact view" option is available in the menu.

Gallery

When you select the "Gallery" view, the app immediately generates the finished gallery and displays a preview.

The gallery consists of a single HTML file that requires no external CSS, JavaScript, or other resources. Only the photos themselves are stored as copies in a separate folder; as a result, the HTML file and the folder can be easily published on the web or viewed locally on your computer—even without the application.

File service

The file service lets the browser-based app browse and manage files through an Express API. The client also provides reusable directory/file models and file-selection dialogs.

Server: server/file-router.js

Initialization and file-system root

The default export is a router factory:

fileRouter({ root, fileRoot, debug, log })

fileRoot takes precedence over root. The app passes config.fileRoot as root. When a root is configured, normalized paths outside it are rejected. Routes that request real-path checks also resolve symlinks before proceeding. root: null uses the process-wide file system path resolution instead of a configured root; the source marks this mode as experimental.

Directory entries whose names start with . are omitted. Each returned entry includes its name, whether it is a directory, its size, and its last-modified time. File-system errors from most routes are passed to Express error handling; /exists responds with false when the path cannot be resolved or inspected.

HTTP API

The routes below are relative to the router mount point (/api in this app). JSON request bodies are used for POST requests.

Route Request Result
GET /dir — Lists the root directory.
GET /dir/*path Path in URL segments Lists the requested directory.
POST /files { "path": "folder/subfolder" } or an array of path segments Lists a directory.
POST /exists { "path": "folder/file" } or { "filename": "folder/file" } File metadata (path, name, isDir, size, time), or false.
POST /mkdir { "path": "folder/new-folder" } or a filename field Creates the directory and missing parent directories; responds with true.
POST /trash { "path": "folder/file" } / { "filename": "folder/file" }, or { "directory": "folder", "files": ["a", "b"] } Moves the target(s) to the operating system trash; responds with true.
POST /open { "filename": "folder/file" }, optionally with "args": [...] Opens a path with the default application, or invokes the named application with arguments; responds with true.
POST /readtextfile { "path": "folder/file" } or a filename field Returns the file contents as text/plain.
POST /write { "path": "folder/file", "content": "..." } or a filename field Writes the content and responds with true.

Directory-list responses have the shape:

{
  "dir": "folder/subfolder",
  "path": ["folder", "subfolder"],
  "resolvedDir": "/absolute/path/to/folder/subfolder",
  "files": [
    { "name": "photo.jpg", "isDir": false, "size": 1234, "time": "..." }
  ]
}

The application also serves files under /api/get as static content from config.staticGet. This is separate from the router and is used by the client to display file previews.

Client: client/file-service/

client/file-service.js re-exports the default object assembled in client/file-service/index.js. That object combines the API functions, file tools, dialogs, translations, and path helpers. The app sets the API base URL to /api during startup; the API module's standalone default is /app/file.

API functions

The functions in file-service-api.js make requests to the configured API base:

  • setURL(url) changes the base URL.
  • getURL(filename) builds a browser URL for a file served from the static /get path, primarily for images and previews.
  • getDir(path = ''), mkDir(path, newDir), exists(filename), readTextFile(filename), writeFile(filename, content), trashFile(filename), trash(directory, files), and open(filename, args) call the corresponding server operations.
  • getFileSystemPath(path) resolves a path through exists and returns the resolved path when available.
  • normalizeFilename(filename) returns the resolved path when available, otherwise a normalized version of the input.

API helpers log request errors to the browser console. The JSON helper and readTextFile return undefined when a request fails.

File and directory models

file-tools.js exports:

  • FileItem, which represents an entry and exposes its parent directory, extension, relative pathName, and absolute filePath.
  • Directory, which stores the current path and entries. Its getDir(path) loads entries via the API, applies its optional filter and sort functions, and returns whether loading succeeded. The default sort puts directories before files, then sorts by name.
  • isValidFilename(name) and isValidDirectoryName(name), which check common filename restrictions, including forbidden characters, trailing dots/spaces, and reserved Windows device names.
  • fileExtension, FileIcon, MIME_GROUPS, and fileIsMime for extension lookup, file icons, and file-type filtering.

Dialogs and UI helpers

file-dialog.js provides SelectController for directory navigation, selection state, and selection events; reusable buttons and dialog components; and higher-level dialogs:

  • selectImageFilesDlg({ dir, header, multiple = true }) selects image files and can show previews.
  • selectFileDialog({ dir, header, mime, filter, multiple = false, event }) selects files, optionally filtered by a MIME group or custom filter.
  • selectSingleFileDialog({ dir, fileName, header, mime, filter }) selects one file and returns its path.
  • selectDirectoryDlg({ dir, header, event }) opens a directory-selection dialog.
  • selectFolderDialog({ dir, header, event }) selects the current or a selected folder and returns its path.

The returned selection from the multi-file dialog is a Directory model containing the selected FileItem entries. Dialogs also support directory creation, deletion to trash, and opening the current location in the operating-system file browser where those controls are included.

The remaining modules provide the <flexible-select> custom element, English/German UI strings, path normalization (joinPaths), cross-platform path parsing (parsePath), sorting helpers, and a small event emitter.

Heartbeat modules

The heartbeat keeps the local Gallery Maker server alive while at least one browser tab is connected. It uses a persistent WebSocket connection; it does not send periodic ping/pong frames.

Server: server/heartbeat-ws.js

initHeartbeat({ server, maxClient = 1, debugLog = true })

Initializes the heartbeat on an existing Node.js HTTP server:

  • Creates a ws WebSocket server in noServer mode and handles HTTP upgrade requests whose URL is exactly /ws-heartbeat.
  • Logs connections and closures when debugLog is enabled.
  • Allows one client by default. When the number of connected clients exceeds maxClient, it sends the extra connection the forbidden message. The client is responsible for closing that connection.
  • When the last client disconnects, schedules server shutdown after two seconds. A new connection during this delay cancels the pending shutdown.
  • If the shutdown timer runs more than four seconds after it was scheduled (for example, because the computer slept), it assumes the system resumed from hibernation and waits another ten seconds for a browser to reconnect. If no client returns, the process exits with code 0.
  • In NODE_ENV=development, watches the public directory recursively. Changes are debounced for one second before a reload message is sent to connected clients.

The module is initialized by the application after the HTTP server starts listening. The server passed in must support the upgrade event.

sendBrowserReload()

Sends the reload message to every connected WebSocket client that is currently open. It does nothing if the heartbeat has not been initialized. In development, the public directory watcher calls this function after a change.

Client: client/heartbeat-client.js

connectHeartbeat(options)

Opens a WebSocket connection to the current page's host at /ws-heartbeat. It selects ws:// for HTTP pages and wss:// for HTTPS pages.

Options are optional:

Option Default Purpose
debug true Enables client-side console logging.
forbiddenText Die App ist in einem anderen Tab geöffnet Text shown when the server rejects an additional tab.
forbiddenClass text-bg-danger p-3 fs-1 CSS class list applied to the rejection message.
appId main ID of the application element to remove when access is forbidden.

On receiving reload, the client reloads the page. On receiving forbidden, it appends the configured message to the document, removes the application element, and closes the socket without reconnecting. On any other socket closure, it tries to reconnect after one second using the same options.

The application imports and calls connectHeartbeat during client startup. The server and client must use the same WebSocket path and message strings.
